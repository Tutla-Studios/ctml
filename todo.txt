CraftyTML - left undone
=======================

Every line is a bug or a caveat that is still true of the code, labelled by how much it matters:

  CRITICAL    silently wrong or leaves the ui stuck, and nothing says so
  WARN        a real limit worth knowing before building on it
  SUGGESTION  a rough edge or a cost, fine as it stands


RENDERER / PAINT  (render/CTMLRenderer.java)
--------------------------------------------
- SUGGESTION: opacity is drawn as a group rather than composited. Everything inside a faded box is drawn
  at the group's alpha, and whatever an opaque square background of the group covers is left out of the
  draws under it, so the ordinary overlap no longer darkens twice. Nothing on the gui side can draw a
  subtree off screen and fade the result, so two translucent children of a faded box, or two under a
  rounded or translucent background, do still show through one another.
- SUGGESTION: a background image is one layer, and how big it is comes from the size read off the front
  of the png, which an <img> is sized from as well. Anything else a texture can be, an atlas sprite
  among them, has no size to cover or contain with: a background is stretched over the whole box
  instead, and an img with no width or height of its own comes out empty. No background-origin, no
  background-attachment, no repeat-space or repeat-round, and a rounded box draws its tiles once per
  row of its corners rather than once.

LAYOUT  (render/CTMLLayout.java)
--------------------------------
- SUGGESTION: a bar takes its room out of the content, so a box that turns out to need one is laid out
  a second time with the room kept. Once only: if keeping the room then makes the other axis overflow,
  that axis's bar floats over the content rather than asking for a third pass.
- WARN: a table collapses its borders by sliding the cells onto one another by the width of the first
  border it finds, so a table whose cells carry different border widths has them overlap by the
  wrong amount. There is no border-spacing, no col or colgroup, and no visible-row collapsing.
- WARN: a float is placed where it was written in the flow rather than on the line it appears on, so one
  written between two words sits above that line instead of inside it. There is no shape-outside.
- WARN: grid has one track list per axis: no named lines, no areas, no subgrid, no dense packing and no
  minmax(). An fr track only has room to share where its axis has a definite size, and an auto
  track is sized from the items sitting in one track alone, not from the ones spanning several.
- SUGGESTION: a list item's marker is one text line the item keeps left of its own content, so it is
  drawn in the item's own colour and font and there is no ::marker to style apart from it. There is no
  list-style-image, and list-inside indents every line of the item rather than only the line the
  marker is on, which shows on an item that wraps.
- SUGGESTION: a multi column block never splits a child down the middle, so its columns are only as even
  as whole children allow and a child taller than its share makes its column taller.


OVERFLOW AND SCROLLING  (render/CTMLScroll.java, render/CTMLFocus.java)
-----------------------------------------------------------------------
- SUGGESTION: scrollIntoView brings a box in from the nearest edge, which is the only alignment there
  is: no block or inline alignment to ask for, and no scroll-margin or scroll-padding to hold the box
  clear of the edge it is brought to.
- SUGGESTION: a scroll of its own picks the anchor afresh, so a resize that lands on the same frame as
  a scroll is not corrected. Css suppresses anchoring around the user's own scrolls as well, but it
  names the cases; this picks a new anchor and waits for the frame after.
- SUGGESTION: tab walks the ring through everything that can take it in one order, and there is no way
  to hold it inside a part of the screen: no focus trap, and no arrow key walking within a group.
  A ring is drawn by ring-*, and anything else about what has the keyboard is a focus: or
  focus-within: class on it.


STYLE SYSTEM  (ctml/ElementStyle.java, ctml/style/*)
----------------------------------------------------
- SUGGESTION: the variants are the ones that can be answered from the element and the screen alone:
  hover, focus, focus-visible, focus-within, active, dark, the breakpoints sm to 2xl and their max-
  halves, and first, last, only, odd and even. Nothing else is one: no group- or peer-, since no
  element watches another's state for it, and no print, motion-reduce or contrast-more, since there
  is no such setting to read. focus-visible is the same as focus, a ctml focus always being drawn.
  The three about the mouse and the keyboard are told to the tree by the screen it is open in, so a
  host that draws a tree itself with CTMLRenderer.render has to say them with setHovered and friends.
- SUGGESTION: the breakpoints are gui pixels rather than css ones, since that is what ctml measures
  in: sm 320, md 480, lg 640, xl 854, 2xl 1024, which puts the usual minecraft window around md and
  lg rather than off the end of css's own 640 to 1536.
- SUGGESTION: dark: asks the nearest element at or above it that set a colour scheme with scheme-dark
  or scheme-light, and Media.dark() where none did. A scheme set behind a variant is not read when
  that question is being answered, so dark:scheme-light says nothing to the element under it.
- SUGGESTION: no box-shadow, outline, cursor, font-family, transform, transition or animation. With no
  font-family there is nothing monospaced to put <code> and <pre> in, so they keep the spacing they
  were written with and leave the look to the classes on them.
- SUGGESTION: there is no way to set defaults from a script, and no per element reset: a new element
  has to override defaultStyle() in java.
- SUGGESTION: an element's styles are three layers, the plain classes under every layer of classes
  whose variants are holding under whatever was set by hand, and reading the class property again
  replaces everything the classes said before it rather than piling onto it, which is what lets a
  callback show a box it had hidden. There is no classList, but the property holds the list the
  element was written with and reads back as it stands, so adding or taking away one class is an
  edit to that string: nothing is lost by having to write it back whole.
- SUGGESTION: gradient colour interpolation modifiers (bg-linear-to-r/oklch, /srgb-linear) are not
  read, and every ramp is mixed channel by channel in plain srgb.
- SUGGESTION: a from- / via- / to- class with no shape class before it assumes bg-linear-to-r, and
  writes the background gradient; the text one is written by text-from- / text-via- / text-to-.


SCREEN AND REGISTRY  (render/CTMLScreen.java, render/UIRegistry.java, CraftytmlClient.java)
-------------------------------------------------------------------------------------------
- SUGGESTION: a drag of a box or of a scrollbar thumb ends on mouseReleased, and there is still no way
  to read the live button state back: this build is on sdl, so there is no glfwGetMouseButton to ask.
  A release that never arrives is worked out from the cursor instead, since a button that is down
  reports every movement it makes, so one that moves with nothing reported lets go within a few
  frames. A release lost while the cursor then never moves again is still held, until it moves or
  anything at all is pressed; nothing moves in the meantime, so it costs nothing but the grip.
- WARN: no hot reload: editing a .ctml file needs a game restart.
- WARN: the events that reach a callback are the three mouse buttons, INPUT from a press or from enter
  or space on a focused button, HOVER as the cursor comes onto an element, and DRAG while a draggable
  one is moved. HOVER is only told about the way in, never the way out; nothing is told about a
  release, a wheel, a key other than enter and space, or an element being scrolled.
- WARN: no text input or scrollable list widget, and no <a>: a link has nowhere to go. Everything else
  is ctml, div, span, img, button, the table tags and the markdown set (h1 to h6, p, ul, ol, li,
  blockquote, pre, code, hr, br, b, strong, i, em, s, del, u, ins). An img has no alt text and nothing
  to say while its texture loads, and a button is a box that can be pressed: it is not disabled by
  anything, and has no pressed or hovered look of its own, so one is written on it with hover: and
  active: like on any other box.
- SUGGESTION: every element ends up with an id, its own or one handed out in order the first time it is
  asked for, and getElementById walks the tree each time it is called rather than keeping a map: a
  tree that changes shape can never hand back something stale, at the cost of a walk per lookup.
